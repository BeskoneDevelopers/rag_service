# Как работает запрос в RAG-сервисе

## Redis Lock и TTL

После поиска API пытается записать в Redis случайный токен командой `SET ... NX EX 180`. `NX` разрешает запись только при свободном ключе. `EX` ставит срок жизни 180 секунд, чтобы ключ исчез даже при падении процесса. Оба маршрута используют один ключ. Если ключ занят, клиент получает 503.

Задача продления запускается примерно раз в 60 секунд. Lua-скрипт сверяет токен владельца и продлевает срок. Сервис прекращает генерацию, если продление не подтверждено. В `finally` другой Lua-скрипт проверяет токен и освобождает ключ. Проверка нужна, чтобы старый запрос не удалил ключ нового владельца.

Генерация дополнительно ограничена `LLM_MAX_TOKENS=512` и независимым абсолютным `LLM_GENERATION_TIMEOUT_SECONDS=60`. Обновление HTTP read timeout или Redis lease не сбрасывает этот лимит; повтор подключения входит в те же 60 с. Обычный клиент ограничивает весь запрос, потоковый — ожидание заголовков и чтение по общему deadline. Контекст блокировки ограничивает также отправку SSE медленному клиенту. HTTP-ответ закрывается при успехе, ошибке, таймауте и отмене, затем выполняется освобождение lock с защитой от отмены. Cleanup ограничен отдельно (HTTP до 5 с, Redis до 3 с); при недоступном Redis остаётся TTL.

## Жизненный цикл SSE

1. API проверяет JWT и компанию, затем получает контекст через Celery.
2. При наличии контекста получает блокировку до отправки HTTP-заголовков. После отправки заголовков статус ответа уже задан.
3. Каждая часть текста отправляется как событие `token`. По подтверждённому завершению проверяются номера ссылок, и `sources` закрывает успешный поток. При сбое поток закрывает `error`.
4. При отключении клиента ASGI-сервер передаёт `http.disconnect`. Обработчик отменяет работу, закрывает чтение из llama-server и освобождает блокировку. Отключение до первого события тоже обрабатывается.

Без релевантных чанков поток отправляет готовую фразу и пустые `sources`. К llama-server этот запрос не обращается.

## Ошибки llama-server и Celery

Клиент llama-server различает отказ подключения, таймаут и ошибку ответа модели. Для обычного API это 503, 504 и 502 соответственно. При обрыве установленного соединения есть одна повторная попытка до первого токена. Когда клиент уже получил текст, повтор мог бы добавить начало нового ответа в тот же поток.

Сбой очереди поиска возвращает 503, истечение времени ожидания Celery — 504, ошибка самой задачи поиска — 502. Для загрузки документа сбой постановки в очередь даёт 503 и оставляет запись со статусом `failed`, чтобы повтор той же загрузки использовал тот же ID.

Исключение `EmbeddingServiceError`, полученное через result backend, обрабатывается отдельно как 503 в обоих маршрутах. Достижение лимита токенов — незавершённый ответ, поэтому клиент возвращает 502 или финальный SSE `error`, а не успешный `sources`.

## Тестирование без моделей

- `httpx.MockTransport` имитирует llama-server. Можно отдать один токен, затем оборвать соединение и проверить, что клиент получает `error` и второго запроса нет.
- Подмена embedding возвращает заранее заданный вектор. Подмена поиска задаёт оценки выше порога, на пороге и ниже него. Так видны точные границы фильтра и порядок ссылок.
- Тесты Redis подменяют команды `SET` и Lua, но запускают два настоящих асинхронных HTTP-запроса к FastAPI. Это проверяет конкуренцию и освобождение блокировки на границе маршрута.
- TTFT и Hit@5 проверяются отдельно. Для них используются установленные модели и реальные данные, чтобы измерения относились к конкретному стенду.


## Повторная доставка индексации

API сохраняет документ со статусом `pending`, затем публикует задачу. После рестарта только API уже опубликованную задачу продолжает выполнять worker. Для сбоя *worker* задача использует `acks_late` и `reject_on_worker_lost`, чтобы Redis мог повторно передать незавершённую обработку. Повторная доставка записи `processing` разрешена, а блокировка строки PostgreSQL предотвращает одновременную запись чанков по одному документу. Если другой worker уже завершил запись, повтор ничего не делает.

Остаётся окно между коммитом документа и публикацией задачи. Защита от него требует transactional outbox или сверки `pending` с очередью. При потере Redis-данных в момент сбоя AOF также не даёт абсолютной гарантии сохранности.

`visibility_timeout=900` установлен согласованно для broker, result backend и Celery; он больше `task_time_limit=600`. `worker_prefetch_multiplier=1` ограничивает резервирование. При гибели всего контейнера возврат не мгновенный: нужен visibility timeout и проход восстановления Redis transport. При гибели дочернего процесса работающего prefork worker действует `reject_on_worker_lost`. Повторно доставленная обработка удаляет прежние чанки и сохраняет новый набор вместе с `completed` одной транзакцией, поэтому незавершённая запись откатывается. Уникальный индекс чанков остаётся дополнительной защитой.

Фактически здесь выполнены тесты с подменами Redis/БД/HTTP. Реальный SIGKILL воркера, переиндексация настоящего DOCX, генерация на Qwen3.5-2B, TTFT и повтор retrieval не выполнены: моделей и корпуса нет, Docker Engine недоступен. Порядок реальной проверки — [verification.md](verification.md). До выполнения этих шагов PR нельзя считать готовым к повторному ревью по всем замечаниям.
